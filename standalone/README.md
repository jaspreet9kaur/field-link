# Field Link ESP32 hub

The ESP32 serves the room and its HTTPS interface. A 2.4 GHz router provides local Wi-Fi. The router can run with its internet connection unplugged, and the laptop can be turned off once the hub has been flashed and provisioned.

## Build and provision on Windows

Use PowerShell 7, Node.js 22 or later, Arduino CLI and the Espressif ESP32 Arduino core. The firmware targets a classic ESP32 Dev Module. The tested core version is 3.3.12. Replace the example COM port and Wi-Fi name with your own values.

    arduino-cli core update-index --additional-urls https://espressif.github.io/arduino-esp32/package_esp32_index.json
    arduino-cli core install esp32:esp32@3.3.12 --additional-urls https://espressif.github.io/arduino-esp32/package_esp32_index.json
    cd standalone
    pwsh -File ./Build-Hub.ps1 -Port COM3
    pwsh -File ./Provision-Hub.ps1 -Port COM3 -Ssid 'YourRouterWiFi'

The provisioning script asks for the Wi-Fi password in a masked prompt and sends it to the ESP32 over USB. It generates the hub HTTPS certificate, writes the public CA under `private/` and records the address and invite codes in `private/hub-access.log`. Keep that folder local. For a stable address, reserve an IP for the ESP32 on your router and complete provisioning after the reservation takes effect. The certificate covers the provisioned IP and `fieldlink.local`, where mDNS is available.

For Android, install a JDK and Android SDK platform 35 with build tools 35.0.0. Set `JAVA_HOME` and `ANDROID_HOME`, then run `pwsh -File ./Build-Apk.ps1 -BundledHub`. This produces a locally signed APK containing the provisioned address and public CA. Omit `-BundledHub` to build a generic APK and enter the hub address on the device.

To build the Windows client, download the pinned Microsoft.Web.WebView2 1.0.4314.35 NuGet package and run `pwsh -File ./Build-Windows.ps1 -SdkPackage <path-to-nupkg>` with the provisioned hub reachable. The build verifies the package hash and pins the hub certificate.

## Join once and use the room

1. Join the router Wi-Fi on both phones. Keep the connection when Android says it has no internet. Airplane mode with Wi-Fi turned back on is suitable for the offline demo.
2. Install **Field-Link-Android-Router.apk** on the Android demo phones. The bundled app knows the hub address and trusts this board's CA. If using the generic APK or a browser instead, transfer **field-link-hub-ca.crt** over USB or Bluetooth and install it as a **CA certificate**. It is distinct from the old laptop-host CA. Do not bypass HTTPS warnings.
3. Open Field Link and join with the member invite and a unique display name. Reserve the operator invite for the demonstrator. A normal laptop browser can also open the ESP32 page after trusting the demo CA.
4. Give Android notification permission, and allow microphone/camera when requested for a call. Under **Options → Alert permissions**, enable full-screen alerts if the phone offers the setting. While the persistent Field Link notification is present, the app attempts to stay on the local room when backgrounded. Lock-screen display depends on the OS, permissions and power management. Android force-stop, an unavailable router, or aggressive battery controls can interrupt alerts. Reopen Field Link after a force-stop or reboot to restart listening.
5. Exchange a text, then try voice, video and a photo. A photo goes into the chat without an accept step. Tap its thumbnail to open the viewer, then **Save to device** to select a location. For the lock-screen test, leave Field Link running on the second phone, lock it, then send a message and place a call. Check notification actions separately from audio/video delivery.

One check means the hub accepted the message. Two gray checks mean the recipient's app received the text or downloaded the photo. Two blue checks mean the item appeared in the recipient's visible conversation. Background alerts carry metadata only. The hub keeps receipt state for its 32 most recent messages in RAM.

Signing in with the operator invite opens **Operator console** by default. It shows the room's online and offline members, animated links between active call participants, connected duration, hub uptime, free memory, reset reason, and the last 12 text/photo transactions. The operator can switch to **Chats** for their own conversations or open the separate **Live location** view. Chat bodies, photos and WebRTC streams stay between the participants. The console covers activity handled by Field Link on this hub.

### Device updates and new controls

The signed Android 0.4.0 package adds Android speaker routing, foreground ringtone, direct links from the glass options sheet into Android settings and location permissions. The application screen and web features are served by the ESP32. An open client checks the hub's build marker on startup and about every 20 seconds, then shows **Update available** when the hub is serving a different build. **Options → Updates** opens the same screen. **Update now** rechecks the trusted hub and loads its interface. Active calls, drafts, photo uploads and location sharing block the reload until they finish. An older installed shell can use the web Options sheet for update and reconnect controls, with instructions for Android-managed settings. Changes to Android-native code or operating system permissions use the platform's signed package update mechanism.

Open **Tele-directory** to find a member and jump straight into their chat. Text and photo history starts with this firmware and is saved on the ESP32 in two rolling 3 KiB segments per conversation. The hub keeps the five latest uploaded photo files across restarts. Older photo entries can outlive their attachments. **Sign out and release seat** removes the hub history associated with the released seat. Keep the seat registered to retain its history.

An active voice call can add and merge one other participant. The host mixes both direct audio legs, so ending the host's original call ends the conference. A one-to-one video call offers mic mute, speaker routing on the updated Android package, camera on/off and front/rear switching when the hardware exposes both cameras. Background ringing uses Android's call notification channel and its system sound settings.

Location sharing is opt-in and foreground-only. A member starts and stops their own feed. The operator sees shared fixes and can grant or revoke access for another named member while the subject is sharing. The hub keeps current fixes and grants in RAM, hides stale positions and clears them on restart. The view shows coordinates, approximate accuracy, age and a relative plot. A phone needs a location fix, and the plot does not download map tiles.

### Windows app

Extract **release/Field-Link-Windows-x64.zip** into a writable folder and open **Field-Link.exe** while Windows is connected to the router's local network. The portable app uses the installed Microsoft Edge WebView2 Runtime and Windows .NET Framework 4.6.2 or later. Use the same member or operator invite with a separate Windows device name. Keep the sibling DLLs and **Field Link Data** folder with the executable. The data folder holds the WebView profile and a Windows user-protected session. Closing the window keeps the app in the notification area. Use **Exit Field Link** from its notification-area menu to quit. Windows notification settings and privacy permissions apply. Windows location sharing requires the PC's location provider to return a position.

The Windows app loads chat, calls, the Tele-directory, the operator console and web updates from the same ESP32. It uses a native save dialog for downloaded photos. The portable EXE is unsigned. To rebuild for a different provisioned hub, obtain the pinned Microsoft WebView2 SDK package from NuGet and run **Build-Windows.ps1** while the trusted ESP32 is reachable.

The app saves the HTTPS origin and stores the device token using Android Keystore. The ESP32 keeps up to eight registered seats in NVS and accepts a saved sign-in after a restart. Sign out to release a seat. A running peer-to-peer call may continue if the board powers off, but a new sign-in or call can't start without it.

Android app permission allows Field Link to request the microphone. WebView, Android's microphone privacy control, and the audio input still have to allow capture. If WebView cannot start capture, the updated APK tries a foreground Android microphone directly. That fallback passes short samples to the call and releases the microphone when the call ends or the app leaves the foreground. **Options → App permissions** opens the system page for Field Link. A hub connection error displays **Reconnecting**. The restart notice requires a valid response with a different boot ID. The board logs its reset reason on USB at 115200 baud.

## Scope, security, and limitations

- The ESP32 handles registration, presence, chat history, photos and call signaling. WebRTC sends microphone/camera streams over the same local network, including the voice conference legs. The hub holds the five most recent compressed JPEGs, up to 100 KB each. The recipient need not accept the photo or be online when it is uploaded. Android can suspend a WebView after its activity leaves the foreground. If a phone cannot open its microphone, video can still start with a working camera and show that it is sending no audio.
- The router must allow direct client communication. The hub stores bounded chat history, accounts and Wi-Fi/TLS setup in local flash. Recent call activity remains in RAM. Phone-to-phone notification and lock-screen behavior must be validated on the actual handsets.
- Room invitations and device tokens are random; the board stores token hashes, and Android uses authenticated Keystore encryption. Members cannot poll other inboxes, download other users' photos or control calls they aren't part of. The operator sees call metadata. Same-origin HTTPS API, host validation, bounded inputs and rates, separate role codes, safe text rendering, exact WebView origin and user-mediated media permissions are in place. The hub validates JPEG signatures, size and frame dimensions before publishing an attachment; the client validates them again before displaying it. The OS asks where to save a copy; there is no unrestricted storage permission.
- No SQL, cookie sessions, URL fetching, JWT, webhooks, CORS grants or source maps. Invite registration is not enterprise identity verification or MFA. The ESP32 flash/NVS is not encrypted by this build. A physical attacker with access to the board should be assumed able to recover its local Wi-Fi/TLS configuration. Remove the demo CA from phones after testing and keep the ESP32 physically controlled.
- The microphone fallback uses existing platform APIs and adds no application libraries. Its Android permission, visible-activity check, call-scoped access and cleanup were source-reviewed. Samples are transient and are never written to files or sent through the hub. A current advisory scan of the existing Android WebView and ESP32 toolchain is separate from the release checks.
- Receipt updates are scoped to the authenticated recipient and current hub boot. A sender sees status only for their own messages. The operator activity payload is gated by the role stored on the ESP32. It contains bounded traffic metadata and omits message bodies, attachments and SDP. The update uses the existing dependencies, bearer sessions, same-origin request validation and rate limits.
- History lookup derives the storage path from the authenticated account and a registered contact. Location lookup checks the viewer's role or a named grant for the subject. Location values are bounded, age out and are never written to the history journal. The update check accepts the same-origin hub build marker and reloads trusted HTTPS assets. The hub flash remains physically readable. No new third-party application dependencies were added.
- The web update check rejects redirects and malformed build markers. Applying an update reloads the current trusted origin after confirmation. The update flow adds no account privileges, storage for tokens, external update source, APK installer or application dependencies.
- The Windows shell reads the ESP32 leaf fingerprint during a build through an HTTPS certificate chain verified against the provisioned CA. At runtime, native HTTPS checks the exact hub certificate and forwards only allowlisted hub routes and bounded payloads into the WebView. It passes through the hub's browser security headers. It changes no Windows certificate stores, rejects redirects and uses DPAPI for the saved bearer token. Build packaging uses Microsoft WebView2 SDK 1.0.4314.35 with a pinned package checksum and relies on the installed WebView2 Runtime for media and browser security updates. Runtime advisory coverage depends on the installed Windows runtime. Windows camera, microphone, GPS, audio output, photo save dialog and tray alerts still need a physical Windows-to-Android run.
